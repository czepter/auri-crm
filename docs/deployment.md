# Deployment

Deployed on [Coolify](https://coolify.io) from `docker-compose.coolify.yml`:
eight application services off three prebuilt images — pulled, never built on
the server — alongside Postgres, Redis, Gotenberg and RustFS from upstream
ones. `docker-compose.yml` beside it stays the local development stack with
its bind mounts and dev dependencies; nothing in the Coolify file is meant to
run on a laptop.

**The compose file is the documentation.** Its header comment carries the
three Coolify parser rules the stack is written against, and every service
carries the reasoning for its own environment block. This document covers
what surrounds it: the image pipeline, the first-deploy sequence, what has to
be configured by hand, and how to roll back. Read the compose file for the
why of any individual line.

## The image pipeline

`.github/workflows/release-image.yml` builds `docker/app/Dockerfile`,
`docker/gallery/Dockerfile` and `docker/mcp/Dockerfile` on every push to
`main` and `dev` that touches `apps/`, `docker/` or the workspace manifests,
and pushes all three to GHCR:

```
ghcr.io/czepter/auri-crm/studio     six services: admin, portal, api, horizon, scheduler, migrate
ghcr.io/czepter/auri-crm/gallery    the Astro SSR gallery
ghcr.io/czepter/auri-crm/mcp        the MCP server's HTTP transport
```

`mcp` is its own image rather than a seventh service on `studio` because it
is a Node program and that image's runtime is FrankenPHP — Node appears there
only in a build stage that is thrown away. Same reason `gallery` is separate.

Building ahead of the deploy rather than on the server is deliberate: a VPS
compiling PHP extensions and two JavaScript bundles while the old containers
are still serving is a bad trade on hardware sized for neither. By the time a
deploy runs, the image is already built, already cached, and already tested
by `ci.yml` on the same commit.

Three tags per build:

| Tag | Moves when | Used for |
|---|---|---|
| `latest` | Only on the default branch | What `docker-compose.coolify.yml` names |
| `<branch>` | Every push to that branch | Trying a branch on a staging stack |
| `sha-<commit>` | Never | Naming one specific deploy — the rollback target |

A `dev` push must never become what production pulls on its next restart,
which is why `latest` is gated on the default branch.

The workflow's first job runs `docker/app/check-coolify-compose.php`, which
enforces Coolify's parser rules against the compose file. It guards the
failure mode nothing else catches: every rule it checks produces a stack that
deploys **green** with an empty secret or a misrouted domain.

Either make the two GHCR packages public, or give the server a registry
login.

## Coolify's three constraints

Summarised here because they explain the file's shape; the header comment has
the detail.

1. **No YAML anchors or merge keys.** Coolify's parser fails on them
   (coollabsio/coolify#2705), which is why every service repeats its
   environment block instead of sharing one. Anything that does not vary per
   deployment was moved into `docker/app/Dockerfile` to keep that repetition
   down to secrets and domains.
2. **A `SERVICE_*` variable is only generated when it is the entire value.**
   `base64:${SERVICE_REALBASE64_APPKEY}` is silently skipped — so `APP_KEY`
   gets its `base64:` marker in `docker/app/entrypoint.sh` instead.
3. **A referenced domain is assigned to whichever service references it.**
   `${SERVICE_FQDN_ADMIN}` written in the `horizon` service would hand the
   admin domain to a container with no web server, which is why Horizon and
   the scheduler take a plain `${APP_URL}`.

Coolify generates each magic variable once and reuses it forever. That is the
only reason `APP_KEY` can be generated at all — a key that rotated per deploy
would invalidate every encrypted column and signed cookie the studio holds.

## Configure by hand

Everything else (`APP_KEY`, the Postgres user and password, the Redis
password, the RustFS key pair) is generated by Coolify on first deploy. These
are not:

| Variable | Set to |
|---|---|
| `APP_URL` | The surface whose links a queued mail should contain — the portal, wherever the mail goes to a client |
| `MAIL_URL` | The outbound SMTP DSN |
| `MAIL_FROM_ADDRESS` | The studio's sending address |
| `STRIPE_WEBHOOK_SECRET` | From the Stripe dashboard's webhook endpoint |
| `STUDIO_SENTRY_DSN` | The GlitchTip project for the Laravel surfaces — leave empty and the SDK stays fully inert |
| `GALLERY_SENTRY_DSN` | The GlitchTip project for the Astro gallery — same |
| `POSTGRES_DB`, `AWS_BUCKET` | Optional; both default to `studio` |

Five domains are assigned by Coolify, one per web-facing service: `admin`,
`portal`, `api`, `gallery` and `mcp`. RustFS gets a sixth, because presigned
URLs handed to a browser have to resolve publicly.

`mcp` needs one because a remote MCP client connects to it directly, and
because the URL *is* the `resource` identifier in the RFC 9728 document it
serves. Nothing about the MCP server is configured by hand: `MCP_PUBLIC_URL`
and `OAUTH_ISSUER_URL` are both `SERVICE_FQDN_*` references Coolify fills in,
and `CRM_API_BASE_URL` stays container-internal because only that container
calls it.

Identifiers in `SERVICE_*` names carry no underscores — Coolify splits the
port off the last one, so `SERVICE_FQDN_MY_APP_8080` reads as the service
"my" on port "app".

## What runs

| Service | Image | Role |
|---|---|---|
| `admin` | studio | `APP_SURFACE=admin` — the staff surface, own domain |
| `portal` | studio | `APP_SURFACE=portal` — the client surface, own domain |
| `api` | studio | `APP_SURFACE=api` — public JSON, own domain |
| `gallery` | gallery | Astro SSR, own domain, reaches `api` internally |
| `mcp` | mcp | MCP HTTP transport, own domain, verifies bearers against `api` internally |
| `horizon` | studio | `php artisan horizon` — every named queue |
| `scheduler` | studio | `php artisan schedule:work` |
| `migrate` | studio | `php artisan migrate --force --isolated`, one-shot |
| `postgres`, `redis`, `gotenberg`, `rustfs` (+ `rustfs-init`) | upstream | Data, PDF rendering, object storage |

`migrate` runs once per deploy and every app container waits on it completing
cleanly, so no surface ever serves a request against a half-migrated schema.
`restart: "no"` is also how Coolify recognises a one-shot and leaves it out
of the deployment health check.

`rustfs-init` exists because RustFS starts empty and the S3 driver will not
create a missing bucket — without it the first upload after a fresh deploy
fails with `NoSuchBucket`. RustFS's bundled console stays off: it is an admin
surface over every object in the studio, and turning it on means a second
public door.

Config caching is deliberately **not** run in the entrypoint —
`config/sentry.php` holds a `ScrubSensitiveData` instance and the cache is a
`var_export` of the config array, which fails outright on a non-serializable
object. See the `ponytail:` note in `docker/app/entrypoint.sh` for what would
have to change to get it back.

## Rolling back

Edit the `image:` lines in `docker-compose.coolify.yml` to name a
`sha-<commit>` tag from a known-good build and redeploy. That tag is the only
one that names a specific deploy; `latest` moves.

A rollback does **not** undo migrations. If the bad deploy changed the
schema, restore from the cutover snapshot instead — see
[studio/docs/cutover-runbook.md](../apps/studio/docs/cutover-runbook.md),
whose `db:cutover-restore` command exists for exactly this.

## First deploy

1. Create the resource in Coolify from `docker-compose.coolify.yml` on the
   `main` branch.
2. Assign the six domains (`admin`, `portal`, `api`, `gallery`, `mcp`,
   `rustfs`).
3. Fill the manual variables above. Leave both Sentry DSNs empty until a
   GlitchTip project exists.
4. Deploy. `migrate` runs the schema, `rustfs-init` creates the bucket, and
   the five web services come up behind their healthchecks.
5. Visit `/einrichtung` on the admin domain and complete first-run setup —
   see "First-run setup" below. No seeder runs in a deploy, and
   `DemoCrmSeeder` is guarded off in production anyway. Everyone after the
   first arrives by invitation.
6. TOTP enrollment is optional, at `/auth/mfa/enroll` on the admin domain —
   nothing blocks the dashboard for staff who skip it.

## First-run setup

A freshly deployed instance has no staff account. The first person to reach
`/einrichtung` becomes the studio's Owner — there is no invite code and no
recovery path if the wrong person gets there first. Complete setup
immediately after deploying, before sharing the URL.

To see the wizard on a local machine that already has a seeded account, run
`php artisan migrate:fresh` first — `db:seed`'s `test@example.com` account
(created only outside production) otherwise makes `/einrichtung` 404 same as
it would once any real Owner exists.
